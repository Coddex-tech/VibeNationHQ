# 1. Purpose

The VibeNation Community System allows users to participate in discussions around music and entertainment content.

Users can:

* create posts about songs, albums, EPs, and artists
* write reviews and opinions
* rate songs and albums
* like community posts
* comment on posts
* reply to comments
* like comments and replies
* follow other users
* follow artists
* favorite songs and albums
* report inappropriate content
* discover community discussions through feeds and music pages

The community system is intentionally separated from VibeNation's editorial system.

Editorial content is created by VibeNation's staff.

Community content is created by platform users.

This distinction is fundamental to the architecture.

---

# 2. Community System Overview

The community system can be understood as several connected layers:

```text
                    VIBENATION COMMUNITY
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
   Community Posts    Music Ratings     Social Graph
          │                │                │
          │                │          ┌─────┴─────┐
          │                │          │           │
          ▼                ▼          ▼           ▼
      Comments       Song Ratings   User Follow  Artist Follow
          │          Album Ratings
          │
          ▼
       Replies
          │
          ▼
       Likes
          │
          ▼
       Reports
```

The primary community content object is:

```text
CommunityPost
```

A post can optionally be connected to a music object through:

```text
CommunityPostTarget
```

Comments and replies belong to posts.

They do not become independent posts.

---

# 3. Core Principles

The community system follows these principles.

## 3.1 Users create community content

Normal community content is generated by authenticated users.

Users can create:

* posts
* comments
* replies
* ratings
* likes
* favorites
* follows

These records should not normally be manually created by administrators.

---

## 3.2 Posts and comments are different content types

A community post is a standalone piece of user-generated content.

A comment exists only as part of a discussion attached to a post.

```text
CommunityPost
    │
    ├── Comment
    │      ├── Reply
    │      │      └── Reply
    │      └── Reply
    │
    └── Comment
```

A comment must never be converted into a standalone community post.

---

## 3.3 Music metadata is not manually entered when possible

When a user wants to write about a song or album, the application should provide a music search interface.

The user searches for the music item and selects it.

The system then stores the appropriate target reference/metadata.

The user should not be required to manually type:

* song title
* artist name
* album name
* provider ID
* artwork URL

when those details are available from the catalog integration.

---

## 3.4 VibeNation does not host music files

The community system is not a music hosting system.

VibeNation does not need to upload or store copyrighted commercial audio files merely to allow users to discuss them.

Music discovery and listening should use approved external provider links and previews where permitted.

---

## 3.5 Engagement records are source-of-truth rows

Likes, ratings, follows, and favorites are represented by database records.

Cached counters may exist for performance, but they are not the source of truth.

For example:

```text
CommunityPostLike rows
        ↓
actual number of likes
        ↓
CommunityPost.likes_count
        ↓
cached display value
```

The row-level records remain authoritative.

---

The main community models are:

```text
CommunityPost

CommunityPostLike

CommunityPostComment
CommunityPostCommentLike
CommunityPostCommentReport

CommunityPostReport

ArtistFollow

```

These models serve different purposes.

| Model                        | Purpose                                   |
| ---------------------------- | ----------------------------------------- |
| `CommunityPost`              | User-created social post                  |
| `CommunityPostTarget`        | Music/content item associated with a post |
| `CommunityPostLike`          | Like on a post                            |
| `CommunityPostComment`       | Comment or reply                          |
| `CommunityPostCommentLike`   | Like on comment/reply                     |
| `CommunityPostCommentReport` | Report on comment/reply                   |
| `CommunityPostReport`        | Report on post                            |

| `AlbumRating`                | User rating of an album                   |

| `AlbumFavorite`              | User favorite album                       |
| `ArtistFollow`               | User follows an artist                    |
| `UserFollow`                 | User follows another user                 |

# 5. Community Posts

## 5.1 What a Community Post Is

A `CommunityPost` is a standalone user-generated publication.

Examples:

```text
"Rema's new single is easily one of his best this year."

"That album had amazing production but the second half felt weak."

"What's your favorite track from this EP?"

"10/10 production. The hook is crazy."
```

A post can contain a user's written content and may be associated with a music target.

The post belongs to the user who created it.

Conceptually:

```text
User
  │
  └── CommunityPost
          │
          └── CommunityPostTarget
                  │
                  └── Song / Album / Artist / External Music Item
```

---

## 5.2 Creating a Community Post

The normal flow is:

```text
User opens Community Composer
        ↓
Searches for music
        ↓
Music results appear
        ↓
User selects music item
        ↓
User writes opinion/review
        ↓
Optional rating
        ↓
User publishes
        ↓
CommunityPost created
```

The frontend should make the music selection feel like part of the post composer rather than forcing the user to manually enter music metadata.

---

## 5.3 Music Selection

The user should be able to search music while composing a post.

For example:

```text
Search:
"Unavailable"

Results:

┌─────────────────────────────────────┐
│ Cover                               │
│ Unavailable                         │
│ Davido                              │
│                                     │
│ ▶ Preview                           │
└─────────────────────────────────────┘
```

The result can contain provider metadata such as:

* title
* artist
* album
* artwork
* provider identifier
* preview URL when available
* official listening URL
* provider name

The user selects the result.

The backend then creates the appropriate `CommunityPostTarget`.

---

## 5.4 Post Ownership

Every community post belongs to the user who created it.

The ownership relationship should be enforced by the backend.

The frontend must never be trusted to determine the owner.

For example:

```text
POST /community/posts/

Authenticated user:
    user_id = request.user.id

Created post:
    author = request.user
```

A client should not be able to submit:

```json
{
    "author": 123
}
```

and impersonate another user.

The server determines ownership from the authenticated session/token.

---

## 5.5 Post Views

Community posts have their own view counter:

```text
CommunityPost.views_count
```

A view represents the post being viewed by a user/client according to the application's view-counting rules.

View increment logic belongs in the API/service layer.

It should not be implemented as a model-side automatic increment.

For example:

```text
GET /community/posts/<id>/

        ↓

View-counting service

        ↓

CommunityPost.views_count += 1
```

The exact anti-abuse strategy can evolve later.

Possible future improvements include:

* authenticated-user deduplication
* anonymous session deduplication
* IP/time-window throttling
* Redis-based view tracking
* batched counter updates

---

## 5.6 Post Likes

Likes are represented by:

```text
CommunityPostLike
```

Conceptually:

```text
User ──────── CommunityPostLike ──────── CommunityPost
```

A user should normally be able to have only one active like on a particular post.

The database should enforce the appropriate uniqueness rule.

The frontend can implement:

```text
Like
↓
Unlike
↓
Like
```

without creating duplicate like records.

---

# 6. Community Post Targets

## 6.1 Why Targets Exist

A community post is not necessarily limited to a VibeNation-owned `Song`, `Album`, or `Artist` record.

A user may discover a song from an external music catalog before that song exists in VibeNation's own database.

Therefore, the system uses:

```text
CommunityPostTarget
```

as an abstraction layer.

This allows the post to reference either:

1. an internal VibeNation music object, or
2. external music-provider metadata.

---

## 6.2 Internal Music Targets

A target can reference an internally known music object.

Examples:

```text
CommunityPost
    ↓
CommunityPostTarget
    ↓
Song
```

or:

```text
CommunityPost
    ↓
CommunityPostTarget
    ↓
Album
```

or:

```text
CommunityPost
    ↓
CommunityPostTarget
    ↓
Artist
```

This is useful when the music item already exists in VibeNation's catalog.

---

## 6.3 External Music Provider Targets

A user may search for a song that has not yet been imported into VibeNation's internal catalog.

Instead of forcing the application to create a complete `Song` record immediately, the target can preserve the external provider information.

Examples of information that may be stored include:

```text
provider
provider_id
title
artist_name
album_name
artwork_url
preview_url
external_url
```

The exact fields must match the finalized `CommunityPostTarget` implementation.

The important architectural principle is that external catalog data should not automatically become authoritative VibeNation catalog data.

---

## 6.4 Target Selection Flow

The complete flow is:

```text
                 USER
                   │
                   ▼
          Search music catalog
                   │
                   ▼
          External provider API
                   │
                   ▼
            Search results
                   │
                   ▼
            User selects item
                   │
                   ▼
        CommunityPostTarget
                   │
          ┌────────┴─────────┐
          │                  │
          ▼                  ▼
   Internal VibeNation   External provider
       object                metadata
          │                  │
          └────────┬─────────┘
                   ▼
             CommunityPost
```

This architecture prevents the community composer from being tightly coupled to one music provider.

# 7. Community Ratings

## 7.1 Rating Scale

Community ratings use a five-star scale.

Supported values:

```text
0.5
1.0
1.5
2.0
2.5
3.0
3.5
4.0
4.5
5.0
```

Ratings are stored separately from posts.

A user may write a post about a song without necessarily rating it, depending on the product rules implemented by the API.

---

## 7.2 Song Ratings

Song ratings are represented by:

```text
SongRating
```

Conceptually:

```text
User
  │
  └── SongRating ──── Song
```

A user's rating belongs to a specific song.

The system should prevent duplicate active ratings by the same user for the same song.

If a user changes their rating:

```text
4.0
 ↓
4.5
```

the existing rating should normally be updated rather than creating another rating record.

---

## 7.3 Album Ratings

Album ratings are represented by:

```text
AlbumRating
```

Conceptually:

```text
User
  │
  └── AlbumRating ──── Album
```

The same uniqueness principle applies:

```text
one user + one album = one active rating
```

The user can change the rating later.

---

## 7.4 Rating Rules

Rating records are user activity.

Therefore:

* users create ratings
* users update their own ratings
* users delete their own ratings
* admins can inspect/moderate ratings
* admins should not normally fabricate user ratings

This is why rating models may intentionally have no normal admin `+ Add` button.

---

## 7.5 Average Rating Calculation

Average ratings are intentionally **not stored as a permanent field** on songs or albums.

For example:

```text
SongRating
    5.0
    4.0
    4.5
    3.5
```

The average can be calculated by the database:

```text
AVG(rating)
```

This prevents the application from having two competing sources of truth.

The source of truth is:

```text
SongRating rows
```

not:

```text
Song.average_rating
```

The API can calculate and return:

```json
{
    "rating_count": 124,
    "average_rating": 4.32
}
```

without permanently storing the average.

---

# 8. Comments and Replies

## 8.1 Comments

Community comments are represented by:

```text
CommunityPostComment
```

A comment belongs to exactly one community post.

```text
CommunityPost
    │
    ├── CommunityPostComment
    ├── CommunityPostComment
    └── CommunityPostComment
```

A comment cannot exist independently of a post.

---

## 8.2 Replies

Replies use the same model:

```text
CommunityPostComment
```

A self-referential parent relationship distinguishes replies from top-level comments.

Conceptually:

```text
CommunityPostComment
    parent = NULL
        ↓
    Top-level comment
```

and:

```text
CommunityPostComment
    parent = another CommunityPostComment
        ↓
    Reply
```

This avoids creating separate `Comment` and `Reply` tables unnecessarily.

---

## 8.3 Deeply Nested Replies

The parent relationship allows nested discussions.

Example:

```text
Comment A
│
├── Reply A1
│   │
│   ├── Reply A1a
│   │
│   └── Reply A1b
│
└── Reply A2
    │
    └── Reply A2a
```

Every reply points to the comment/reply immediately above it.

For example:

```text
Reply A1a.parent = Reply A1
```

not directly to the original comment.

This allows arbitrary discussion depth.

The frontend can choose how many levels to display initially.

For performance and usability, the UI may later collapse deeply nested branches and load them on demand.

---

## 8.4 Comments Are Not Posts

This rule is critical.

A comment:

```text
belongs to a CommunityPost
```

A post:

```text
exists as an independent community publication
```

Therefore:

```text
Comment → cannot become Post
Reply → cannot become Post
```

If the product eventually supports "quote/repost" functionality, that should be implemented as a separate feature rather than treating comments as posts.

---

## 8.5 Comment Views

Community comments have:

```text
views_count
```

This allows VibeNation to track engagement with individual comments/replies where the product requires it.

View counting belongs to the API/service layer.

The model itself should not automatically increment its own counter merely because it was retrieved.

---

## 8.6 Comment Likes

Likes on comments/replies use:

```text
CommunityPostCommentLike
```

The relationship is:

```text
User
  │
  └── CommunityPostCommentLike
              │
              ▼
      CommunityPostComment
```

This works for both top-level comments and nested replies because replies are represented by the same comment model.

---

# 9. Community Engagement

## 9.1 Likes

VibeNation separates likes by content type.

For community posts:

```text
CommunityPostLike
```

For community comments:

```text
CommunityPostCommentLike
```

Editorial content has its own corresponding like models.

This separation makes permissions, queries, moderation, and future scaling clearer.

---

## 9.2 Favorites

Users can favorite music objects.

Current favorite models include:

```text
SongFavorite
AlbumFavorite
```

Conceptually:

```text
User
 │
 ├── SongFavorite ─── Song
 │
 └── AlbumFavorite ── Album
```

Favorites represent a personal relationship with music rather than public social engagement.

Depending on product requirements, favorite counts may be displayed publicly.

---

## 9.3 Follows

The community system supports two different kinds of following:

```text
UserFollow
ArtistFollow
```

These represent completely different relationships.

---

## 9.4 Artist Following

An artist is a VibeNation catalog/editorial entity.

An artist is **not a Django User**.

There is no requirement for an artist to have:

* an account
* a password
* login credentials
* a user profile
* a Django user record

Instead:

```text
User
  │
  └── ArtistFollow ─── Artist
```

This allows users to follow artists even though those artists do not have accounts on VibeNation.

For example:

```text
Victor
  │
  └── follows ─── Artist: Burna Boy
```

The artist record remains a catalog entity.

---

## 9.5 User Following

Users can follow other users through:

```text
UserFollow
```

Conceptually:

```text
Follower User
      │
      ▼
 UserFollow
      │
      ▼
Followed User
```

A user should not be able to follow themselves.

The database constraint should enforce this rule.

User following can later power:

* personalized feeds
* following timelines
* notifications
* social discovery
* profile activity
* recommendation systems

---

# 10. Reports and Moderation

## 10.1 Why Reporting Is Separate

Reports are moderation records.

They should not be mixed with the content they report.

For example:

```text
CommunityPost
       ▲
       │
CommunityPostReport
```

The post remains the original content.

The report records the moderation event.

This allows multiple users to report the same content without modifying the content record itself.

---

## 10.2 Reportable Content

Community content currently supports reports for:

### Posts

```text
CommunityPostReport
```

### Comments and Replies

```text
CommunityPostCommentReport
```

Reports may contain information such as:

* reporting user
* reported object
* reason
* description/details
* moderation status
* timestamps

The exact fields should follow the finalized model implementation.

---

## 10.3 Moderation Flow

A typical moderation flow is:

```text
User sees problematic content
        ↓
User submits report
        ↓
Report record created
        ↓
Staff/Admin reviews report
        ↓
Decision
   ┌────┼─────┐
   │    │     │
   ▼    ▼     ▼
Ignore Remove Warn/Action
```

Moderators should investigate the report rather than automatically deleting content simply because a report exists.

The final action depends on VibeNation's moderation policy.

# 11. Community Feed

The community feed is a presentation layer built primarily around:

```text
CommunityPost
```

A future feed can combine:

* posts from followed users
* posts about followed artists
* trending posts
* recent posts
* popular posts
* posts about recently discussed songs/albums
* personalized recommendations

For example:

```text
                 CommunityPost
                       │
       ┌───────────────┼────────────────┐
       │               │                │
       ▼               ▼                ▼
 Followed Users   Followed Artists   Trending
       │               │                │
       └───────────────┼────────────────┘
                       ▼
                  Feed Ranking
                       │
                       ▼
                   User Feed
```

The feed should not require a separate permanent `FeedPost` table unless a future requirement makes materialization necessary.

Initially, the feed can be generated from existing community relationships and indexed queries.

# 12. Editorial Content vs Community Content

VibeNation has two distinct content systems.

## Editorial

Created by:

```text
VibeNation staff/admin
```

Examples:

* music reviews
* news articles
* editorial features
* artist stories
* album analysis

Model:

```text
EditorialArticle
```

## Community

Created by:

```text
VibeNation users
```

Model:

```text
CommunityPost
```

The systems can interact.

For example:

```text
EditorialArticle
     │
     └── Comments
```

and:

```text
CommunityPost
     │
     └── Comments
```

But they should remain separate content domains.

This keeps editorial authority distinct from user-generated content.

# 13. External Music Catalog Integration

The community composer can integrate with external music catalog providers.

The recommended architecture is:

```text
Frontend
   │
   ▼
VibeNation API
   │
   ▼
Music Provider Adapter
   │
   ├── Apple Music / Apple catalog
   ├── Optional secondary provider
   └── Optional metadata enrichment
```

The frontend should preferably communicate with VibeNation's backend rather than embedding provider-specific API logic everywhere.

This provides several advantages:

* API keys remain server-side
* provider changes are easier
* provider-specific response formats stay isolated
* rate limiting can be controlled
* caching can be managed centrally
* external provider failures can be handled gracefully

---

## Provider abstraction

A provider adapter can normalize different responses into a common structure.

For example:

```python
{
    "provider": "apple_music",
    "provider_id": "...",
    "type": "song",
    "title": "...",
    "artist_name": "...",
    "album_name": "...",
    "artwork_url": "...",
    "preview_url": "...",
    "external_url": "..."
}
```

The community system should not depend on one provider's exact response format.

# 14. Audio and Copyright Policy

The community system does not require VibeNation to host commercial music files.

The intended architecture is:

```text
VibeNation
    │
    ├── stores metadata
    ├── stores editorial/community content
    └── links to approved external listening services
```

It should not become:

```text
VibeNation
    │
    └── stores copyrighted MP3 files
```

External previews, artwork, and provider links must always be used according to the applicable provider's current terms.

The application should not:

* download commercial audio from providers
* permanently cache restricted preview audio
* expose provider audio as VibeNation-owned files
* provide unauthorized full-track streaming
* bypass provider restrictions

The preview player should be treated as a provider-integrated discovery feature rather than a VibeNation music-hosting system.

### Important limitation

A provider preview does not necessarily mean VibeNation can arbitrarily select any 10-second portion of a full song.

If a provider supplies a fixed preview segment, the application should use that preview according to the provider's permitted behavior.

Arbitrary playback from any point in a commercial track is a separate licensing problem and should not be assumed to be available through a metadata API.

# 15. Cached Engagement Counters

Several community-related models contain cached counters.

Examples:

```text
CommunityPost.likes_count
CommunityPost.comments_count
CommunityPost.views_count

CommunityPostComment.likes_count
CommunityPostComment.replies_count
CommunityPostComment.views_count
```

These counters exist primarily for read performance.

They are not independent sources of truth.

For example:

```text
CommunityPostLike
    │
    ├── row
    ├── row
    ├── row
    └── row
          ↓
      COUNT(*)
          ↓
likes_count
```

The application should update counters atomically when appropriate.

For example:

```python
CommunityPost.objects.filter(pk=post_id).update(
    likes_count=F("likes_count") + 1
)
```

The exact implementation belongs in the service/API layer.

---

## Counter repair

Because counters are cached values, administrative or maintenance commands may eventually be provided to recalculate them.

For example:

```text
actual CommunityPostLike rows
        ↓
COUNT(*)
        ↓
rebuild CommunityPost.likes_count
```

This provides a recovery mechanism if a bug ever causes a counter to become inaccurate.

---

# 16. API Responsibilities

The API layer is responsible for enforcing community business rules.

Typical responsibilities include:

### Authentication

Verify that the request comes from an authenticated user where required.

### Ownership

Ensure users can modify only their own content.

### Uniqueness

Prevent duplicate:

* likes
* favorites
* follows
* ratings

where the model requires uniqueness.

### Validation

Validate:

* rating ranges
* post content
* comment content
* target information
* parent comment relationships

### Counters

Update cached engagement counters atomically.

### Views

Handle view-counting logic.

### Moderation

Create report records and enforce moderation restrictions.

### Permissions

Prevent unauthorized users from editing or deleting content.

---

# 17. Security and Ownership Rules

Community content is user-generated and therefore must be treated as untrusted input.

The backend must never trust:

```text
author_id
user_id
owner_id
```

submitted by the client when ownership can be derived from authentication.

Instead:

```python
request.user
```

should determine the acting user.

---

## Ownership examples

A user may:

```text
edit own post
delete own post
edit own comment
delete own comment
change own rating
remove own like
remove own favorite
```

A user should not normally be able to:

```text
edit another user's post
delete another user's comment
change another user's rating
remove another user's follow
```

Staff/admin permissions are handled separately.

---

## Parent validation

When creating a reply, the backend must verify that the parent comment belongs to the appropriate community post.

The system should not allow a malicious client to construct invalid relationships such as:

```text
Post A
   │
   └── Reply
         parent = Comment belonging to Post B
```

The API must validate the entire relationship.

---

# 18. Performance and Scalability

The community system is expected to grow substantially over time.

The initial architecture should therefore use normal relational database relationships and proper indexes rather than prematurely introducing complex infrastructure.

PostgreSQL is the intended production database.

Important query patterns should be indexed appropriately.

Examples include:

```text
posts by author
posts by creation date
comments by post
replies by parent
likes by user + post
ratings by user + song
ratings by user + album
follows by follower
follows by followed user
artist follows by artist
```

Pagination should be used for:

* community feeds
* comments
* replies
* reports
* user activity
* ratings where exposed
* followers/following lists

Large discussion threads should never require loading every reply at once.

---

## Caching

Redis or another caching layer can eventually be used for:

* trending posts
* feed results
* popular music
* frequently requested comments
* view counting
* rate limiting

Caching should complement PostgreSQL rather than replace it as the source of truth.

---

## Future Go services

If community traffic becomes large enough, high-concurrency workloads can later be moved to specialized services.

Possible candidates include:

```text
Feed generation
View counting
Real-time notifications
Trending calculations
High-volume engagement processing
```

Django/DRF remains responsible for core business logic until there is a demonstrated reason to split services.

Do not introduce Go simply because the system might eventually become large.

# 20. Developer Workflow

When implementing a new community feature, follow this general process.

## Step 1 — Identify the content

Determine whether the feature concerns:

```text
Post
Comment
Reply
Music
User
Artist
Editorial content
```

Do not put unrelated responsibilities into one model.

---

## Step 2 — Identify the relationship

Ask:

```text
Who owns it?
What does it belong to?
Can it exist independently?
Can it be nested?
Is it an engagement record?
```

---

## Step 3 — Enforce important rules at the database level

Examples:

```text
one user → one rating per song
one user → one rating per album
one user → one like per post
one user → one follow relationship
user cannot follow themselves
```

Database constraints should protect the system even if an API bug occurs.

---

## Step 4 — Put business logic in the service/API layer

Do not rely on models to perform complex side effects.

Examples:

```text
create like
remove like
create rating
delete rating
increment views
create report
follow artist
follow user
```

These operations belong in the appropriate application/service/API layer.

---

## Step 5 — Update cached counters atomically

Whenever engagement changes:

```text
create like
     ↓
increment counter
```

or:

```text
delete like
     ↓
decrement counter
```

Use atomic database operations where appropriate.

---

## Step 6 — Add API tests

Test at minimum:

```text
authenticated user can create post
anonymous user cannot create post
user cannot edit another user's post
user cannot create duplicate like
user can unlike
user can create comment
user can reply to comment
deep replies work
invalid parent relationships are rejected
ratings are validated
duplicate ratings are prevented
reports can be submitted
```

# 21. Golden Rules

These rules should be treated as architectural invariants.

### Rule 1 — Community posts are user-generated content

```text
CommunityPost = social/user content
```

---

### Rule 2 — Comments are not posts

```text
Comment → belongs to Post
Reply → belongs to Comment
```

Never treat a comment as an independent post.

---

### Rule 3 — Artists are not users

```text
Artist ≠ Django User
```

Artists are catalog/editorial entities.

Users follow artist records through:

```text
ArtistFollow
```

---

### Rule 4 — Music metadata should be provider-assisted

Users should select music from search results rather than manually entering metadata whenever possible.

---

### Rule 5 — VibeNation does not host commercial MP3 files

The community system is for discussion, discovery, ratings, and social interaction—not unauthorized music hosting.

---

### Rule 6 — Engagement rows are the source of truth

Examples:

```text
CommunityPostLike
SongRating
AlbumRating
SongFavorite
AlbumFavorite
ArtistFollow
UserFollow
```

Cached counters are optimizations.

---

### Rule 7 — Do not store average ratings unnecessarily

Calculate averages from rating records.

```text
AVG(SongRating.rating)
AVG(AlbumRating.rating)
```

---

### Rule 8 — Ownership comes from authentication

Never trust client-submitted user IDs for ownership-sensitive operations.

Use:

```python
request.user
```

---

### Rule 9 — Validate nested relationships

A reply must belong to the same discussion tree as its parent post.

Never trust a client to construct arbitrary parent relationships.

---

### Rule 10 — Admins moderate; users generate engagement

Admins should manage and moderate the platform.

They should not normally fabricate:

* likes
* ratings
* follows
* favorites
* comments

The community creates its own engagement.

---

### Rule 11 — Keep providers replaceable

The community system should not be permanently tied to one external music provider.

Use provider adapters and `CommunityPostTarget` to isolate external metadata.

---

### Rule 12 — Build for scale without prematurely overengineering

Start with:

```text
Django
DRF
PostgreSQL
proper indexes
pagination
atomic updates
```

Add Redis, background workers, Go services, or other infrastructure when actual workload justifies them.

# Final Mental Model

The easiest way to understand VibeNation's community architecture is:

```text
                         USER
                          │
             ┌────────────┼─────────────┐
             │            │             │
             ▼            ▼             ▼
       CommunityPost   Ratings       Social Graph
             │         │      │       │       │
             │         │      │       │       │
             ▼         ▼      ▼       ▼       ▼
          Target     Song   Album   User    Artist
             │       Rating Rating Follow   Follow
             │
       ┌─────┴──────┐
       │            │
       ▼            ▼
   VibeNation    External
    Music       Provider
       │            │
       └─────┬──────┘
             ▼
      Community Discussion
             │
             ▼
         Comments
             │
             ▼
          Replies
             │
             ▼
           Likes
             │
             ▼
          Reports
```

In short:

```text
Music gives the community something to talk about.

CommunityPost gives users a place to express themselves.

CommunityPostTarget connects that discussion to music.

Comments and replies create conversation.

Ratings express opinions quantitatively.

Likes and favorites represent engagement.

Follows create the social graph.

Reports provide moderation.

PostgreSQL stores the source of truth.

The API enforces the rules.

The admin system moderates the platform.

External music providers supply discovery metadata and permitted listening/preview links.

VibeNation itself owns the community experience—not the copyrighted music files.
```

This separation is what allows the community system to grow from a simple comment/review feature into a much larger social music platform without turning the database into one giant, tightly coupled model.
